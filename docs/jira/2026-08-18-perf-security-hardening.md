## T29 · เลิกยิง Auth ทุกครั้งที่แตะฐานข้อมูล

**Type:** Bug · **Priority:** Highest · **Epic:** E17 · **Commit:** `a6b23ed`

### ที่มาของปัญหา

`auth.getUser()` **ไม่ใช่** การอ่าน token ในเครื่อง — มันยิง HTTP ไป `/auth/v1/user` ทุกครั้งที่เรียก เพื่อให้เซิร์ฟเวอร์ยืนยันลายเซ็น

ในโค้ดเดิมมันถูกเรียกจากฝั่ง client **15 ไฟล์** และหนักที่สุดคือ `uid()` ใน `lib/storage.ts` ซึ่งถูกเรียกนำหน้า **7 ฟังก์ชันฐานข้อมูล** — เท่ากับแทบทุก query มี auth round-trip นำหน้าหนึ่งครั้ง เปิดสตูดิโอครั้งเดียวจึงยิง auth หลายสิบครั้ง

### สิ่งที่ทำ

`lib/current-user.ts` (ไฟล์ใหม่) อ่าน JWT ที่เบราว์เซอร์ถืออยู่แล้วผ่าน `getSession()` แคชไว้ในหน่วยความจำ และรวม caller ที่มาพร้อมกันให้เหลือการอ่านครั้งเดียว (สตูดิโอ mount หลาย component พร้อมกัน) · ล้างแคชผ่าน `onAuthStateChange` จึงไม่มีทางค้างหลัง sign-out

### ทำไมยังปลอดภัย

client ใช้ user id ไป **กรอง query ของตัวเอง** เท่านั้น ไม่ได้ใช้ตัดสินสิทธิ์ — ตัวกันจริงคือ RLS ที่ฐานข้อมูล ซึ่งตรวจ token เองและไม่เชื่อสิ่งที่ client บอก

ยืนยันเพิ่มระหว่างการตรวจความปลอดภัย: token ที่ถูกปลอมใน localStorage จะถูก PostgREST ปฏิเสธที่ลายเซ็น ดังนั้น id ฝั่ง client กับตัวตนจริงแยกจากกันแบบใช้ประโยชน์ไม่ได้ · ฝั่ง server (`proxy.ts`, route handlers) ยังใช้ `getUser()` เหมือนเดิม เพราะตรงนั้นการยืนยันคือขอบเขตความปลอดภัยจริง

### ผลลัพธ์ที่ผู้ใช้เห็น

สตูดิโอเปิดเร็วขึ้นและไม่ค้างตอน Auth ช้า

### เงื่อนไขการตรวจรับ

- [x] client เรียก `getUser` : 15 ไฟล์ → 0
- [x] server ยังเรียกครบทุกจุดที่เป็นด่านความปลอดภัย
- [x] เทสต์กันไหลกลับ (`lib/__tests__/auth-calls.test.ts`) ฟ้องทันทีถ้ามี client module เรียกอีก หรือถ้า `currentUser()` เผลอเปลี่ยนไปยิงเน็ตเอง

## T30 · เอาประวัติย้อนกลับออกจากแถวโปรเจกต์

**Type:** Bug · **Priority:** Highest · **Epic:** E17 · **Commit:** `27d94be` · **Migration:** `0032`

### ที่มาของปัญหา (วัดบนฐานข้อมูลจริง)

| ตัวชี้วัด | ค่า |
|---|---|
| ตาราง `fittbuilder_projects` | 56 MB |
| ในนั้นเป็นคอลัมน์ `history` | **31 MB** |
| โปรเจกต์หนักสุด (ETAX_SYC) | `files` 361 kB · `history` 3,116 kB → **89% ของแถวคือประวัติ undo** |
| upsert ตาราง projects | เฉลี่ย **200 ms** สูงสุด **517 ms** |
| query อื่นทั้งหมดใน `pg_stat_statements` | ต่ำกว่า 1 ms |

`SELECT` ดึง `history` มาทุกครั้งที่เปิดโปรเจกต์ และ `projectToRow` เขียนกลับทุกครั้งที่เซฟ

### ทฤษฎีที่ผิด (บันทึกไว้เพื่อไม่ให้มีคนลองซ้ำ)

policy RLS ทุกอันเรียก `auth.uid()` แบบไม่ห่อ `(select ...)` ซึ่งเป็นข้อผิดพลาดยอดฮิตของ Supabase จึงตั้งสมมติฐานว่านี่คือต้นเหตุ **เบนช์มาร์กที่ 2,000 แถวแล้วพบว่าไม่ใช่:**

| แบบ | เวลา (warm) |
|---|---|
| `auth.uid()` ต่อแถว (ของเดิม) | 32.4 ms |
| `(select auth.uid())` ยกเป็น InitPlan | 32.9 ms |

ตัวที่แพงคือ helper function ซึ่งถูกเรียกต่อแถวอยู่ดีทั้งสองแบบ (~16 µs/แถว → ที่ 56 โปรเจกต์คิดเป็น ~1 ms ต่อ query) **ฝั่ง engine ไม่ใช่ปัญหา — ปัญหาคือขนาดข้อมูลที่ขนข้ามเน็ต**

### ทำไมไม่ใช้ `project_revisions` ที่มีอยู่แล้ว

`fittbuilder_project_revisions` (0025) เก็บ snapshot เหมือนกันและมี sha + label แต่เก็บสถานะ **หลัง** เปลี่ยน ขณะที่ undo ต้องการสถานะ **ก่อน** เปลี่ยน · และ `applyDeps` (แก้ package.json) push history โดยไม่สร้าง revision — สลับ undo ไปอ่าน revisions ตรงๆ จะทำให้ undo บางกรณีข้ามไปไกลกว่าหนึ่งขั้น

### สิ่งที่ทำ

stack ย้ายไปอยู่หลังสองฟังก์ชันใน migration `0032`:

| ฟังก์ชัน | หน้าที่ |
|---|---|
| `fittbuilder_history_push(pid, snapshot)` | เก็บสแนปช็อต เก็บไว้สิบอันล่าสุด คืนความลึกใหม่ |
| `fittbuilder_history_pop(pid)` | ถอนอันล่าสุด ตั้งเป็น `files` ของโปรเจกต์ แล้วคืนค่าให้ |

- สำเนาทั้งสิบไม่ออกจากฐานข้อมูลอีก client บอกแค่ "เก็บอันนี้" กับ "ขออันล่าสุดคืน"
- `history_count` (4 ไบต์) ตอบว่าปุ่ม Undo กดได้ไหม — ตามแบบ `file_count` ใน `0027`
- pop กับการเขียน `files` อยู่ในสเตทเมนต์เดียว undo จึงลงครึ่งทางไม่ได้
- ทั้งสองฟังก์ชันเป็น `SECURITY INVOKER` ให้ `projects_update` เป็นด่านเดิมที่การเซฟธรรมดาผ่าน
- **สแนปช็อตถูกส่งเข้าไป ไม่ใช่ให้ฟังก์ชันอ่านจากแถวเอง** เพราะการเซฟถูก debounce ไว้ แถวในฐานข้อมูลจึงยังตามหลังสิ่งที่กำลังจะเก็บอยู่หนึ่งขั้น

### ผลลัพธ์ที่วัดได้

| โปรเจกต์ | เปิดครั้งหนึ่ง (เดิม) | เปิดครั้งหนึ่ง (ใหม่) | ลดลง |

## T31 · ตรวจความปลอดภัยทั้ง branch

**Type:** Task · **Priority:** High · **Epic:** E17

ตรวจเฉพาะสิ่งที่ branch `feat/domain-skill-templates` เพิ่มเข้ามา (quote v2, partner leads, org brand, project versions, admin skills, auth refactor)

### พบ 1 ข้อ — ยังไม่ได้แก้

**Host-header injection → ลิงก์คำเชิญในอีเมลชี้ไปโดเมนของผู้โจมตีได้** (`lib/origin.ts:8`)

`requestOrigin()` เชื่อ header `x-forwarded-host` แบบไม่ตรวจ แล้วค่านั้นถูกประกอบเป็น `inviteLink` ที่ส่งออกไปในอีเมล (`app/api/invite-email/route.ts:37`, `app/api/org-invite-email/route.ts:36`) · ผู้ใช้ที่ล็อกอินปกติเชิญอีเมลใดก็ได้ แล้วยิงคำขอเองพร้อม `X-Forwarded-Host: evil.com` → เหยื่อได้อีเมลจากผู้ส่งที่เชื่อถือได้ของเรา พร้อมลิงก์ไปหน้า login ปลอม

**ทางแก้:** อ่าน origin จาก `PUBLIC_SITE_URL` เป็นหลัก ให้ header เป็นแค่ fallback ตอน dev แล้วตั้ง env ใน Cloud Build trigger ทั้ง prod และ sandbox — **ต้องขอค่าโดเมนจริงทั้งสองจากผู้ใช้ก่อน**

### ตรวจแล้วสะอาด

`0029`/`0030`/`0031` (trigger ปักหมุด `is_partner` ได้จริง · partner leads เข้าถึงได้เฉพาะ service role · policy UPDATE มี `with check` ครบ · bucket โลโก้บล็อก SVG) · route ที่ใช้ service role ทุกตัวตรวจสิทธิ์ผ่าน RLS ก่อน · `/api/generate` ตรวจ `projectId` ก่อนดึง Org DNA · admin gate ครบทุกจุด · ไม่มี secret ใน git · `dangerouslySetInnerHTML` มีจุดเดียวและไม่มี input ผู้ใช้

### เรื่องที่ไม่ใช่ช่องโหว่แต่ควรเอาออก

`public/Claude-Code-CyberSecurity-Skill-main/` (2.4 MB) + `.zip` (1.6 MB) ถูก commit เข้า `public/` ซึ่งเสิร์ฟที่ root ของโดเมน — ชุดเครื่องมือ offensive security ดาวน์โหลดได้จากโดเมนโปรดักชันโดยไม่ต้องล็อกอิน
