## T2 · [บั๊กร้ายแรง] แชร์โปรเจกต์แล้วเจ้าของกลายเป็นคนที่เข้ามาดู

| | |
|---|---|
| **Type** | Bug |
| **Priority** | **Highest** |
| **Epic** | E6 Workspace, Members & Sharing |
| **Release / วันที่** | v0.44.2 · 2026-08-03 |
| **Status** | Done |
| **Commit** | `5b80566` · migration `0024_lock_project_owner.sql` |

**ปัญหา / ที่มา**
ผู้ใช้รายงานว่า "เพื่อนทำงานอยู่แล้วแชร์ให้คนอื่น พอคนอื่นเปิดดู โปรเจกต์กลายเป็นของคนนั้นเฉยเลย" — เจ้าของงานเสียสิทธิ์ในงานตัวเองโดยไม่ได้ทำอะไรผิด และเจ้าของเดิมกลายเป็นเพียงสมาชิก

สาเหตุมี **สองชั้นและต้องแก้ทั้งคู่**:
1. **ฝั่งแอป** — ฟังก์ชันบันทึกอัตโนมัติส่ง `owner_id` ไปด้วยทุกครั้ง ซึ่งเป็น id ของ "คนที่กำลังบันทึก" ไม่ใช่เจ้าของจริง พอผู้ที่ถูกแชร์เปิดโปรเจกต์แล้วระบบ autosave ทำงาน เจ้าของก็ถูกเขียนทับทันที
2. **ฝั่งฐานข้อมูล** — RLS policy สำหรับ UPDATE มีแต่ `USING` ไม่มี `WITH CHECK` แปลว่าฐานข้อมูลตรวจแค่ว่า "คุณมีสิทธิ์แก้แถวนี้ไหม" แต่ไม่ได้ตรวจว่า "แถวหลังแก้ยังถูกต้องอยู่ไหม" — จึงยอมให้เขียน owner_id เป็นใครก็ได้

**สิ่งที่ทำ**
- ตัด `owner_id` ออกจาก payload ของ `projectToRow()` ทั้งหมด — client ไม่มีทางส่งค่านี้ได้อีกเลย ตอนสร้างโปรเจกต์ใหม่ใช้ค่า default ของฐานข้อมูล (`auth.uid()`) ซึ่งตรงกับ RLS insert check เสมอ
- migration `0024`: เพิ่ม `WITH CHECK` ให้ UPDATE policy และเพิ่ม **BEFORE UPDATE trigger** ที่ตรึงคอลัมน์ที่ห้ามเปลี่ยน — แม้จะมีใครยิง SQL ตรงเข้ามาก็เปลี่ยนเจ้าของไม่ได้
- ซ่อมข้อมูลของโปรเจกต์ที่ถูกกระทบแล้วให้กลับไปเป็นเจ้าของเดิม (Patiphan) โดยใช้ `session_replication_role = replica` เพื่อข้าม trigger สำหรับการซ่อมครั้งเดียว

**ผลลัพธ์ที่ผู้ใช้เห็น**
- แชร์โปรเจกต์ให้ใครก็ได้ เจ้าของไม่เปลี่ยนอีกต่อไป ไม่ว่าอีกฝ่ายจะแก้ไขหรือแค่เปิดดู
- โปรเจกต์ที่เคยเสียเจ้าของไปแล้วถูกคืนให้เจ้าของเดิม

**Acceptance criteria**
- ผู้ที่ถูกแชร์ (editor) เปิดโปรเจกต์ + แก้ไข + ปล่อยให้ autosave ทำงาน → `owner_id` ต้องไม่เปลี่ยน
- ยิง UPDATE ตรงเข้าฐานข้อมูลด้วยสิทธิ์ผู้ใช้ทั่วไปเพื่อเปลี่ยน `owner_id` → ต้องถูกปฏิเสธ
- โปรเจกต์ที่ถูกกระทบต้องกลับไปแสดงเจ้าของเดิมในหน้ารายการโปรเจกต์

# ส่วนที่ 2 · Wand — แก้ไขด้วยการชี้ (E14)

## T3 · Wand เฟส 1–3 — ชี้ที่ element ในพรีวิวแล้วแก้ตรงจุดนั้น

| | |
|---|---|
| **Type** | Story |
| **Priority** | **Highest** |
| **Epic** | E14 Wand & Direct Editing |
| **Release / วันที่** | v0.45.0 · 2026-08-03 |
| **Status** | Done |
| **Commits** | `f0ad2bd` (เฟส 1–2) · `3e3ef4a` (เฟส 3 + UX) · migration `0025_project_revisions.sql` |

**ปัญหา / ที่มา**
การแก้ไข demo ต้องพิมพ์อธิบายด้วยภาษาคนว่า "ตรงไหน" ก่อนจะบอกได้ว่า "แก้เป็นอะไร" — เช่น "ปุ่มสีเขียวมุมขวาบนของการ์ดที่สาม ในหน้ารายการออเดอร์" ซึ่งยาว เสี่ยงสื่อสารผิด และ AI ก็อาจไปแก้ผิดที่ ผู้ใช้เสนอเองว่าอยากได้ฟีเจอร์ชื่อ **Wand** ที่ "เหมือนการเสก" — เลือก element แล้วแก้ได้เลย

**ข้อจำกัดทางเทคนิคที่ต้องออกแบบรอบ:** พรีวิวรันใน iframe แบบ cross-origin ตัว studio จึง **อ่าน DOM ของ demo ไม่ได้และ hit-test ไม่ได้เลย** ทุกอย่างต้องรันอยู่ "ข้างใน" iframe แล้วสื่อสารกลับด้วย `postMessage`

**สิ่งที่ทำ**
- **การชี้เป้าที่แม่นระดับบรรทัด** — เขียน Babel plugin ใน `vite.config.js` ที่ประทับ `data-fitt-loc="src/…/File.tsx:บรรทัด:คอลัมน์"` ลงบนทุก JSX element (เฉพาะโหมด dev) → Wand เลือกได้เฉพาะสิ่งที่ map กลับไปยังบรรทัดโค้ดจริงเท่านั้น ไม่มีทางเลือกโดน element ที่แก้ไม่ได้
- **สคริปต์ overlay ในฝั่ง demo** (`WAND_SCRIPT`) — hit-test, วาดกรอบเรืองแสงตาม element ที่เมาส์ชี้, ส่งพิกัดกลับมาให้ studio วางกล่องคำสั่ง
- **แท็บ "ปรับเร็ว"** — สี พื้นหลัง ขนาดตัวอักษร ระยะห่าง ความมน และการแก้ข้อความ ทำเป็น **การแก้ซอร์สโดยตรงแบบไม่เรียก AI** (`lib/wand-patch.ts` — `patchClassName`, `patchText`, `mergeClasses` ที่รู้จักกลุ่มคลาส Tailwind) → เห็นผลทันทีผ่าน HMR ไม่กินโควตา
- **แท็บ "เสก"** — ส่งให้ AI พร้อม context ที่แคบมาก: ไฟล์ บรรทัด แท็ก คลาส และข้อความปัจจุบันของ element นั้น
- **checkpoint ต่อการแก้** — migration `0025` สร้างตาราง `project_revisions` เก็บ snapshot แบบ content-addressed (SHA-256 ของ canonical JSON ของ file map ตัด 7 hex แรก เหมือน git tree hash) เพราะ **WebContainer รัน git ไม่ได้เลย** · การแก้เร็วๆ ซ้ำๆ บน element เดิมภายในเวลาสั้นจะ amend revision เดิมแทนที่จะสร้างใหม่ ไทม์ไลน์จึงอ่านรู้เรื่อง · จำกัด 30 revision ต่อโปรเจกต์ด้วย trigger

**ผลลัพธ์ที่ผู้ใช้เห็น**
- กดปุ่ม Wand แล้วเลื่อนเมาส์บน demo → กรอบเรืองแสงจับ element ให้เอง พร้อมป้ายบอกไฟล์และบรรทัด
- คลิกล็อกเป้า → กล่องคำสั่งลอยขึ้นข้างจุดนั้น เลือกได้ว่าจะปรับเร็ว (ทันที ฟรี) หรือเสก (ใช้ AI)
- ทุกการแก้มีรหัสเวอร์ชันย้อนกลับได้
- กด Esc ออกจากโหมดได้ทุกขั้น

**Acceptance criteria**
- เลื่อนเมาส์บน demo ต้องเห็นกรอบจับ element พร้อมป้าย `ไฟล์:บรรทัด` ที่ตรงกับโค้ดจริง
- ปรับเร็ว (เช่นเปลี่ยนสีพื้นหลัง) ต้องเห็นผลในพรีวิวโดยไม่เรียก AI และต้อง Undo ได้
- element ที่คลาสถูกคำนวณด้วยโค้ด (ปรับเร็วไม่ได้) ต้องแจ้งเหตุผลและพาไปแท็บ "เสก" พร้อมข้อความตั้งต้น
- ทุกการแก้ต้องสร้าง revision ที่ย้อนกลับได้ และการแก้ซ้ำบน element เดิมภายในเวลาสั้นต้องรวมเป็น revision เดียว

- **แก้รอยต่อของ gradient** — สาเหตุจริงคือ **gradient แนวทแยงไม่มีทางปูซ้ำแบบไร้รอยต่อได้** เพราะที่ตำแหน่ง y เดียวกัน ขอบซ้ายและขอบขวาของ tile อยู่คนละจุดบนแกน gradient · แก้โดยเปลี่ยนเป็น 90deg + สีแรก = สีสุดท้าย + tile คงที่ 600px + ระยะเคลื่อนเท่ากับ 1 tile พอดี
- **`patchText` รองรับ expression เดี่ยว** — `{2}`, `{'ข้อความ'}` ไม่ใช่แค่ข้อความเปล่า พร้อมรักษารูปแบบ quote เดิม และใส่ quote ให้เมื่อตัวเลขกลายเป็นข้อความ · ถ้าค่ามาจากตัวแปรหรือฟังก์ชัน (`{unread}`, `{fmt(total)}`) จะปฏิเสธและบอกเหตุผลว่า "ค่านี้มาจากที่อื่นในโค้ด" แทนที่จะแก้แล้วไม่มีอะไรเปลี่ยน
- **วางกล่องคำสั่งจากขนาดจริง** — เดิมสมมติว่าการ์ดสูง 300px แต่แท็บปรับเร็วสูงราว 440px · เปลี่ยนเป็นวัดขอบเขตจริง เลือกวางล่างก่อน ไม่พอค่อยขึ้นบน แล้ว clamp ทั้งสองแกน โดยหัวการ์ดตรึงไว้และเนื้อในเลื่อนได้

**ผลลัพธ์ที่ผู้ใช้เห็น**
- ปุ่ม Wand เด่นชัดว่าเป็นปุ่มเวทมนตร์
- ตอนเสกเห็นชัดว่าระบบกำลังทำงานที่ element ไหน
- คลื่นไล่สีต่อเนื่องไม่มีรอยต่อ
- แก้ตัวเลขบนป้ายแจ้งเตือนได้แล้ว
- กล่องคำสั่งอยู่ในจอเสมอไม่ว่าจะเลือก element ตรงไหน

**Acceptance criteria**
- เลือก element ที่อยู่ล่างสุดของหน้ายาวๆ → กล่องคำสั่งต้องอยู่ในจอทั้งใบ กดปุ่มล่างสุดได้
- แก้ค่าที่เขียนเป็น `{2}` ต้องสำเร็จและยังคงเป็น expression
- แก้ค่าที่มาจากตัวแปร ต้องไม่แก้เงียบๆ แต่ต้องแจ้งและพาไปแท็บเสก

## T5 · Wand — ทำได้ทีละรอบ (บั๊กแชทหายและระบบค้าง)

| | |
|---|---|
| **Type** | **Bug** |
| **Priority** | **Highest** |
| **Epic** | E14 Wand & Direct Editing |
| **Release / วันที่** | v0.47.0 · 2026-08-05 |
| **Status** | Done |
| **Commit** | `b2d4698` |

**ปัญหา / ที่มา**
ผู้ใช้รายงาน: "เพื่อนกดเสกไปแล้วรอบนึง AI กำลังทำงานอยู่ แล้วใช้อีกรอบตอนที่กำลังทำงาน จู่ๆ แชทนั้นหายไปเลยแล้วไม่ทำงานอะไรเลย"

สาเหตุ: ฟังก์ชัน `generate()` **ไม่มีการกันเรียกซ้อน** และแต่ละรอบถือ "ภาพนิ่ง" ของโปรเจกต์ที่ถ่ายไว้ตอนตัวเองเริ่ม รอบที่จบทีหลังจะบันทึกทับด้วยภาพนิ่งของตัวเองซึ่งไม่เคยเห็นอีกรอบเลย:

```
A เริ่ม:  working = ไฟล์ + ข้อความA
B เริ่ม:  working = ไฟล์ + ข้อความA + ข้อความB
A จบ:    persist(A + คำตอบA)   → ข้อความ B หายจากแชท
B จบ:    persist(B + คำตอบB)   → คำตอบ A หาย + งานที่ A แก้ถูกย้อนคืน
```

และ `finally` ของรอบ A ยังปิดสถานะ streaming ล้างแผงสตรีม และล้าง abort controller ทั้งที่ B ยังวิ่งอยู่ → หน้าจอดูว่างเปล่าและ **กดหยุด B ไม่ได้อีกเลย** ตรงกับ "ไม่ทำงานอะไรเลย"

**สิ่งที่ทำ** — เลือก "ทีละรอบ" ไม่ทำ queue
- **ใส่การ์ดที่ `generate()` เอง** — ทุกทางเข้าวิ่งผ่านฟังก์ชันนี้หมด (แชท, Wand, แก้ error, จัดโครงสร้าง, สร้างไฟล์ที่ขาด, เพิ่มดัชนี) กฎจึงอยู่ที่เดียว
- **`castWand` ตรวจก่อนด้วย** เพื่อไม่ให้ element ที่เลือกไว้หลุด (เดิม `.finally` จะล้างทิ้ง = ผู้ใช้ต้องไปจิ้มใหม่ฟรีๆ)
- **`applyWandPatch` (ปรับเร็ว) ตรวจด้วย** — patch ที่เขียนระหว่างสตรีมจะถูกทับตอนรอบที่วิ่งอยู่บันทึก
- **WandComposer มีสถานะ `locked`** — เดิมมีแต่แผงนี้ที่ยังดูกดได้เวลามีรอบอื่นทำงาน ตอนนี้แท็บปรับเร็วจาง ปุ่มขึ้น "รอรอบที่กำลังทำอยู่" พร้อมแถบเหลืองอธิบาย และเลือก element ไว้ก่อนได้

**เหตุผลที่ไม่ทำ queue (บันทึกไว้เพื่ออนาคต):** prompt ของการแก้ไขถูกประกอบจาก**ไฟล์ปัจจุบัน** คิวไว้แล้วค่อยส่งคือส่งบนไฟล์ที่ยังไม่มี · และ Wand ถือ `ไฟล์:บรรทัด` ติดไปด้วย รอบแรกอาจย้าย/แยกไฟล์นั้นไปแล้ว → **คิวจะไปแก้ผิดบรรทัดแล้วรายงานว่าสำเร็จ** ซึ่งแย่กว่าการบล็อก

**ผลลัพธ์ที่ผู้ใช้เห็น**
- กดเสกซ้อนไม่ได้อีกแล้ว แต่เลือก element ไว้ก่อนได้ พอรอบก่อนเสร็จกดต่อได้ทันที
- ข้อความในแชทไม่หายอีก และงานที่แก้ไปแล้วไม่ถูกย้อนคืน
- ถ้าอยากยกเลิกรอบที่ค้าง กดปุ่มหยุดได้ตามปกติ

**Acceptance criteria**
- ระหว่าง AI ทำงาน กดเสกอีกครั้ง → ต้องขึ้นข้อความแจ้งและ **ไม่เริ่มรอบใหม่** โดย element ที่เลือกไว้ยังอยู่
- ระหว่างรอบที่เริ่มจากที่อื่น (แชท/แก้ error) การ์ด Wand ต้องแสดงสถานะล็อกและกดส่งไม่ได้
- หลังรอบแรกเสร็จ ข้อความในแชทต้องครบทั้งสองรอบและไฟล์ต้องเป็นผลของทั้งสองรอบ

```
[plugin:vite:import-analysis] Failed to resolve import "./components/Sidebar" from "src/App.tsx"
```

สาเหตุ: ข้อความจริงอยู่ใน **`<vite-error-overlay>` ซึ่งเป็น shadow DOM** ที่ระบบเราไม่เคยอ่าน

**สิ่งที่ทำ**
- `ERROR_SCRIPT` อ่านเข้าไปใน shadow root ของ Vite error overlay ดึงข้อความจริงพร้อมชื่อไฟล์และบรรทัดมาแสดง และส่งอันนี้ให้ AI แทน
- **แถบแจ้งเตือนเหลือแถบเดียว** — แสดงเฉพาะอันที่ actionable ที่สุด ส่วนที่เหลือยุบเป็นปุ่ม "ดู error" ถ้าอยากอ่านข้อความเต็ม
- ระงับการรายงาน error ระหว่างที่สตรีมไฟล์อยู่ (module graph กลางสตรีมไม่สมบูรณ์เป็นเรื่องปกติ) แล้ว reload iframe หลังจบเพื่อรายงานเฉพาะ error ที่ยังเหลืออยู่จริง

**ผลลัพธ์ที่ผู้ใช้เห็น**
- จอขาวแล้วรู้ทันทีว่าเพราะอะไร ที่ไฟล์ไหน บรรทัดไหน
- กด "ให้ AI แก้เลย" แล้ว AI ได้ข้อมูลที่แก้ได้จริง
- ไม่มีแถบซ้อนกันจน demo ตกจอ

**Acceptance criteria**
- ทำให้ demo คอมไพล์ไม่ผ่าน → แถบต้องแสดงข้อความ error จริงจาก Vite พร้อมไฟล์และบรรทัด
- กรณีที่มีทั้งไฟล์หายและ compile error ต้องเหลือแถบเดียว
- error ที่เกิดชั่วคราวระหว่างสตรีมต้องไม่ขึ้นแถบ

ทั้งสองประโยคจริงพร้อมกัน: **ไม่มีอะไรบอกแท็บว่ามีการ deploy** และ **ตัวเอกสาร HTML ถูกแคชได้** — รีเฟรชธรรมดาจึงอาจได้ HTML ของ build เก่ากลับมา ซึ่ง script tag ข้างในชี้ไปยัง chunk ของ build เก่าต่อ · ในหน้า studio บันเดิลเก่านั้นยังเป็นเจ้าของ WebContainer ที่กำลังรันอยู่ ซึ่งสคริปต์ bridge ถูกเขียนตอน boot — จึงเป็นที่มาของธรรมเนียม hard reload ในทีม

**สิ่งที่ทำ**
- `/api/version` รายงานเวอร์ชันของ build ที่เซิร์ฟเวอร์รันอยู่ (อ่านจาก `latestVersion()` = หัวของ CHANGELOG)
- `VersionWatcher` เทียบกับเวอร์ชันที่คอมไพล์อยู่ในบันเดิลของตัวเอง — **ตอน mount, ตอนกลับมาที่แท็บ, และทุก 10 นาที** แล้วขึ้นแถบล่างจอพร้อมปุ่ม "โหลดใหม่" (ปิดได้ต่อเวอร์ชัน ต่อแท็บ)
- **แก้ต้นเหตุ**: ตั้งเอกสารเป็น `no-store` ส่วน `/_next/static` ยังคง immutable caching ไว้ — รีเฟรชธรรมดาจึงได้ของใหม่เอง

**ผลลัพธ์ที่ผู้ใช้เห็น**
- มี deploy ใหม่แล้วรู้เอง ไม่ต้องมีใครบอกใน LINE
- รีเฟรชธรรมดาได้ของใหม่ ไม่ต้อง hard reload อีก

**Acceptance criteria**
- deploy เวอร์ชันใหม่ขณะที่แท็บเปิดค้าง → ภายใน 10 นาที (หรือทันทีที่กลับมาที่แท็บ) ต้องขึ้นแถบแจ้งเตือน
- กด "โหลดใหม่" ต้องได้บันเดิลใหม่จริง
- ปิดแถบแล้วต้องไม่ขึ้นอีกสำหรับเวอร์ชันเดิมในแท็บนั้น

**ผลลัพธ์ที่ผู้ใช้เห็น**
- เมนู ⋯ → "คลังหน้าจอ (ใบเสนอราคา)" กดสแกนครั้งเดียว ระบบไล่เปิดทีละหน้าและเก็บภาพให้เอง
- หน้าเข้าสู่ระบบและหน้าเลือกบริษัทถูกเก็บด้วย เพราะเป็นหน้าจอที่ต้องพัฒนาเหมือนกัน

**บั๊กสำคัญ 3 อันที่เจอระหว่างทาง:**
1. **"อัดแล้วไม่มีอะไรเกิดขึ้น"** — การเริ่มอัดจะปิดแผงคลังหน้าจอเพื่อให้เห็นพรีวิว แต่ **ตัวรับภาพอยู่ในแผงนั้น** พอปิดแผง listener ก็ถูก unmount → demo ส่งภาพมาทุกหน้าแต่ไม่มีใครรับ · ย้ายตัวรับไปอยู่ที่ Studio ซึ่งอยู่ยืนยาวกว่าแผง และเพิ่มตัวนับสดในแถบอัด ("เก็บแล้ว 7 หน้า — ล่าสุด: ใบเสร็จรับเงิน") เพราะการไม่รู้ว่ามันทำงานอยู่ไหมคือครึ่งหนึ่งของปัญหา
2. **"29 ภาพกลายเป็น 1 หน้า · 28 ย่อย"** — ช่อง `parent` ตอบ 2 คำถามพร้อมกัน: "เป็น modal ของหน้านี้" (แกลเลอรีเอาไปซ้อน) และ "เดินมาจากหน้านี้" (ผัง Flow เอาไปวาดลูกศร) · โหมดอัดใส่ค่าหลังทุกภาพ → ทุกภาพเลยเป็นลูกของหน้าแรก · **แยกเป็น `parent` (ซ้อน) และ `from` (ลูกศร)**
3. **modal ถูกบันทึกเป็นหน้าจอธรรมดา** — ตอนอัดไม่มีภาพ "ก่อน/หลัง" ให้เทียบ ตัวตรวจจึงคืนเลเยอร์ fixed อันแรกที่เจอ ซึ่งมักเป็นแถบหัวเรื่อง sticky · เปลี่ยนเป็นเลือกเลเยอร์บนสุดที่มีหัวข้ออยู่ข้างในจริง

## T15 · ดัชนีหน้าจอ — ให้แอปประกาศหน้าจอของตัวเอง แทนที่เราจะเดา

| | |
|---|---|
| **Type** | Story |
| **Priority** | **Highest** |

| **Release / วันที่** | v0.47.0 · 2026-08-05 |
| **Status** | Done |

**ปัญหา / ที่มา**
ผู้ใช้ตั้งคำถามที่ตรงจุดที่สุดของทั้งสัปดาห์: *"ในเมื่อเรามี panel code เราเอามาใช้ร่วมได้ไหมครับ ตอนนี้คุณใช้อะไรในการอ่านอ่ะครับ เพราะคุณหาปุ่มแต่ละหน้าไม่เจอซักที DOM หรอครับ ถ้าโค้ดคุณก็น่าจะรู้นะว่าแต่ละหน้าเรียกอะไรใช้งานยังไง"*

คำตอบตามตรงคือ: การสแกนอัตโนมัติ**อ่านโค้ดจริง** แต่เอาไปทำแค่ "ข้อความบนเมนู" แล้วกลับไปหาข้อความนั้นใน DOM — **สะพานคือตัวหนังสือ ไม่ใช่โค้ด** พอเมนูพับ/เป็นไอคอน/สิทธิ์ไม่ถึง ก็ขาดตรงนั้นทันที

**สิ่งที่ทำ**
- **สัญญาใหม่ในการ generate โค้ด (SCREEN INDEX)** — ทุกแอปที่ระบบสร้างต้อง render "ประตู" ที่ซ่อนไว้:
  ```tsx
  <div data-fitt-index style={{ display: "none" }}>
    <button data-fitt-screen="ใบแจ้งหนี้" onClick={() => { setUser(ADMIN); setPage("invoices"); }} />
  </div>
  ```
  `onClick` ต้องพาไปถึงหน้านั้นได้จริง **จากสถานะเริ่มต้นในคลิกเดียว** (ล็อกอิน + เลือกบริษัท + สลับหน้า ครบในนั้น) · อยู่ทั้งใน ARCHITECTURE ของ prompt ตอน build และตอนแก้ทุกครั้ง
- **หัวใจของการแก้ปัญหา modal**: ปุ่มดัชนีของ modal อยู่ในไฟล์ที่เป็นเจ้าของ state ของมัน → มันอยู่ใน DOM **เฉพาะตอนหน้านั้นเปิดอยู่** แปลว่า "modal ที่เจอตอนนี้ = modal ของหน้านี้" โดยไม่ต้องใช้ heuristic ใดๆ เลย
- **`__fittIndexWalk`** — กดประตูทีละบาน รอหน้านิ่ง ถ่าย เดิน modal ของหน้านั้น ปิด กลับ · **ประตูที่กดแล้วแอปไม่ขยับจะถูกรายงานเป็นข้อบกพร่อง** แทนที่จะเก็บสำเนาของหน้าก่อนหน้าใส่ชื่อใหม่
- **ปุ่ม "เพิ่มดัชนีหน้าจอ"** สำหรับโปรเจกต์ที่สร้างก่อนสัญญานี้ — AI ใส่ย้อนหลังให้ใน 1 รอบ โดยไม่กระทบหน้าตา demo แม้แต่พิกเซลเดียว
- **ตรวจความครบกับไฟล์จริง** (`47f7f00`) — "AI ใส่ดัชนีแล้ว" กับ "ดัชนีครบ" เป็นคนละเรื่อง และเดิมเห็นแค่เรื่องแรก · โครงสร้างที่เราบังคับไว้ทำให้นับได้จากชื่อไฟล์ตรงๆ (1 ไฟล์ใน `src/pages/` = 1 หน้าจอ, `*Modal.tsx`/`*Drawer.tsx`/`*Dialog.tsx` รวมพหูพจน์ = ไฟล์ที่ต้องมีประตู) → แถบแจ้ง **"ประกาศไว้ 11/23 หน้าจอ · 4/16 modal"** พร้อมปุ่ม "เติมดัชนีให้ครบ" ที่ส่งรายชื่อไฟล์จริงเข้าไปใน prompt ให้ AI ไล่กา

**ผลลัพธ์ที่ผู้ใช้เห็น**
- ปุ่ม "แคปทุกหน้า (N)" เป็นปุ่มหลัก — ไม่ต้องเดินเมนู ไม่ติดสิทธิ์ ไม่ต้องกางกลุ่มเมนู
- เห็นตัวเลขความครบเทียบกับไฟล์จริง ไม่ต้องเชื่อว่า AI ใส่ครบ
- โปรเจกต์ใหม่มีดัชนีมาให้เองตั้งแต่แรก

**Acceptance criteria**
- โปรเจกต์ที่มีดัชนีครบ กด "แคปทุกหน้า" → ต้องได้ภาพครบทุกหน้าจอและทุก modal ที่ประกาศไว้
- ประตูที่กดแล้วหน้าไม่เปลี่ยน ต้องขึ้น error ที่ระบุว่า onClick ตั้ง state ไม่ครบ **และต้องไม่แคป**
- โปรเจกต์เก่ากด "เพิ่มดัชนีหน้าจอ" → ต้องได้ปุ่มซ่อนครบและหน้าตา demo ต้องไม่เปลี่ยน
- แถบความครบต้องตรงกับจำนวนไฟล์ `src/pages/*` และ `*Modal.tsx` จริง

**ปัญหา / ที่มา**
ผู้ใช้ส่งภาพมาว่าหน้า 02–06 ทุกใบถ่ายผ่าน modal "บันทึกการวิ่งใหม่" ที่ค้างอยู่ และมี error 5 บรรทัด "กดแล้วหน้าไม่เปลี่ยน — modal อาจไม่ได้เปิดจริง"

**อาการเดียวแต่เป็นบั๊ก 3 ตัวซ้อน และตัวที่สามคือรากของทุกเรื่อง modal ที่บ่นมาทั้งสัปดาห์:**

`fixedLayers()` — ฟังก์ชันที่มีหน้าที่หา "เลเยอร์ fixed บนจอ" — เปิดหัวด้วย:
```js
if (!el.offsetParent) continue;   // ใช้เป็นตัวเช็ค "ยังแสดงผลอยู่ไหม"
```
แต่ตามสเปก CSSOM **`offsetParent` เป็น `null` เสมอเมื่อ element นั้นเป็น `position: fixed`** และ modal backdrop ก็คือ `position: fixed` เป๊ะๆ

> ฟังก์ชันที่มีหน้าที่หาเลเยอร์ fixed → ทิ้งเลเยอร์ fixed ทุกตัว → คืน `[]` ทุกหน้า **ตลอดมา**

ทุกอย่างที่ต่อจากมันพังเป็นทอดๆ: `openDialog()` ไม่เจอ → ปิดไม่ได้ → ค้างข้ามหน้า และตอนอัดการใช้งาน modal ก็ถูกบันทึกเป็นหน้าจอธรรมดา

**สิ่งที่ทำ**
- **`visible()`** วัดจากกล่องจริง (`getBoundingClientRect` = 0 เมื่อ `display:none` หรือหลุด DOM และถูกต้องกับ `fixed`) + เช็ค `visibility`/`opacity` — แทน `offsetParent` **ทั้ง 10 จุด**
- **บันไดปิด modal ที่ตรวจผลทุกขั้น** — ปุ่มยกเลิก/ปิด → ปุ่มไอคอนไม่มีข้อความที่มุมบนของ dialog → Escape ทั้ง document และ element ที่โฟกัส → คลิกมุม backdrop · **ถ้าปิดไม่ได้จริงๆ หยุดเก็บ modal ของหน้านั้นแล้วบอกออกมา** ไม่ลากต่อไปหน้าถัดไป
- **`blockingLayer()`** ใช้พื้นที่ปกคลุม (กว้าง ≥80% สูง ≥60%) แทน "fixed + มีหัวข้อ" ซึ่งแถบ sticky ก็เข้าเงื่อนไข · และต้องมีปุ่ม/ช่องกรอกข้างใน เพราะพื้นหลัง gradient เต็มจอก็ fixed และคลุมจอเหมือนกัน — สิ่งที่แยก dialog ออกจากวอลเปเปอร์คือ**มันกดได้**
- **modal ระดับแอป (เช่นเปิดจากหัวเว็บได้ทุกหน้า) เดินชื่อละครั้งเดียว** — เดิมลองเปิดทุกหน้า → สำเร็จ 1 ล้มเหลว 5 ซึ่งคือ 5 บรรทัดแดงพอดี
- **ภาพ modal ตัดกรอบเท่าหน้าจอ** — modal เป็น `position:fixed` สูง 1 จอ แต่หน้าเบื้องหลังยาว 6 จอ ถ่ายทั้ง body จึงได้ภาพยาวที่มี modal เป็นจุดเล็กข้างบน
- **เทสต์กันซ้ำ**: `scaffold-scripts.test.ts` แกะสคริปต์ที่ฉีดเข้า preview ทั้ง 4 ตัวมา `new Function()` เพื่อเช็คว่าเป็น JS ที่ parse ได้, เช็คว่าไม่มี `${` ค้าง (ซึ่งจะถูก interpolate เงียบๆ แล้วส่ง JS พังลงคอนเทนเนอร์ทั้งที่ compile เขียว) และ **แดงทันทีถ้า `offsetParent` โผล่กลับมา**

**ผลลัพธ์ที่ผู้ใช้เห็น**
- modal ถูกตรวจเจอ ปิดได้ และไม่ค้างข้ามหน้าอีก
- ภาพ modal อยู่ในกรอบพอดี ไม่ยาวเฟื้อย
- โหมดอัดบันทึก modal ซ้อนใต้หน้าแม่ถูกต้อง (แก้อาการที่บ่นมาหลายวัน)

**Acceptance criteria**
- แคปหน้าที่มี modal → หน้าถัดไปต้องสะอาด ไม่มี modal ค้าง
- ภาพ modal ต้องสูงเท่าหน้าจอ ไม่ใช่ความสูงของทั้งหน้า
- modal ระดับแอปต้องปรากฏครั้งเดียวใต้หน้าแรกที่เจอ ไม่ใช่ล้มเหลว N−1 ครั้ง
- เทสต์ต้องแดงถ้ามีใครใส่ `offsetParent` กลับเข้าไปในสคริปต์ที่ฉีดเข้า preview

**ปัญหา / ที่มา**
คลังหน้าจอเก็บภาพได้แล้ว แต่ **ปลายทางที่แท้จริงคือใบเสนอราคา** ซึ่งยังไม่มี ผู้ใช้ต้องเอาภาพไปทำเอกสารเองข้างนอก ซึ่งเป็นจุดที่งานหลุดมือ — และโมเดลราคาที่ตกลงกันไว้คือ **S/M/L → man-day → เรต → รวม + VAT**

**สิ่งที่ทำ**

*เฟส 2 — ตารางราคา (`lib/quote.ts` เขียนเป็น pure function ทั้งไฟล์ ทดสอบได้)*
- รายการถูก **หว่านมาจากคลังหน้าจอ** แล้วจากนั้นเป็นของคนเสนอราคา ไม่ใช่ของระบบ
- **modal เป็นบรรทัดของตัวเอง** แสดงเยื้องใต้หน้าแม่ — การยุบ modal เข้าไปในหน้าแม่คือวิธีที่ใบเสนอราคาขาดไปครึ่ง
- ขนาด S/M/L → จำนวนวัน → เรตต่อวัน → รวม → ส่วนลด → VAT → ทั้งสิ้น · **เลขทุกตัวคำนวณย้อนด้วยมือได้** เพราะลูกค้าต้องอ่านออกถึงจะเชื่อ
- **กดเปลี่ยนขนาด → จำนวนวันรีเซ็ตตามขนาดนั้น** เพราะการปล่อยเลขเก่าค้างใต้ป้ายใหม่คือวิธีส่งราคาผิดแบบเงียบๆ
- เพิ่มรายการเองได้ สำหรับงานที่ไม่ใช่หน้าจอ (API, ย้ายข้อมูล, deploy) ซึ่งเป็นเหตุผลหลักที่ใบเสนอราคาที่นับแต่หน้าจอมักตีราคาขาด
- แคปใหม่แล้วมีหน้าเพิ่ม → **"ซิงค์จากคลังหน้าจอ (+N)" เติมเฉพาะที่ขาด ไม่เขียนทับราคาที่แก้ไว้**
- **ยอดรวม = ผลบวกของบรรทัดที่ปัดเศษแล้ว** ไม่ใช่บวกทศนิยมเต็มแล้วค่อยปัด — ไม่งั้นลูกค้าเอาเครื่องคิดเลขไล่คอลัมน์แล้วไม่ตรง และเขามีสิทธิ์ถาม
- ทุกตัวเลขถูก sanitise — พิมพ์ค้างกลางคัน ยอดไม่กลายเป็น NaN

*เฟส 3 — เอกสารพิมพ์*
- `QuotationPrint.tsx` render ผ่าน portal ลง `document.body` + print stylesheet ที่ซ่อน sibling ทุกตัว → ⌘P → "Save as PDF" ได้ A4 ที่มี หัวเอกสาร · ผู้เสนอ/เรียน · ตารางรายการ · ยอดรวม · เงื่อนไข · ช่องเซ็นชื่อ และ **ภาพหน้าจอทั้งหมดเป็นภาคผนวกท้ายเล่ม**
- **ไม่ใช้ไลบรารี PDF ไม่ render ฝั่งเซิร์ฟเวอร์** — ใช้เส้นทางที่ทุก OS มีอยู่แล้ว และพิมพ์ออกมาตรงกับที่เห็นบนจอ
- เอกสารเป็นสีอ่อนเสมอ ไม่ตามธีมมืด และใช้ค่าสีตรงๆ ไม่ใช่ token — **การเปลี่ยนธีมต้องไม่แก้เอกสารที่ส่งไปแล้ว**

*ที่เก็บข้อมูล — เหตุผลเชิงออกแบบที่สำคัญ*
- migration `0026` สร้างตาราง `project_quotes` (1 แถวต่อ 1 โปรเจกต์, payload เป็น jsonb)
- **เก็บในตารางของตัวเอง ไม่ใช่ใน `project.files`** เพราะทุกรอบที่แก้โค้ด ไฟล์ทั้งหมดถูกส่งให้ AI อ่านและเขียนใหม่ — **ราคาที่ลูกค้าเซ็นต้องแตะไม่ได้จากฝั่งที่เขียนแอป**
- RLS ตามสิทธิ์โปรเจกต์ · UPDATE มีทั้ง `USING` และ `WITH CHECK` เพื่อไม่ให้ย้ายแถวไปโปรเจกต์อื่น
- `parseDoc()` ถือว่า payload ที่อ่านกลับมาเป็น **input ที่ไม่น่าเชื่อถือ** (โครงสร้างแถวเคยเปลี่ยนไปแล้วครั้งหนึ่งระหว่างสร้างฟีเจอร์นี้) — อะไรที่อ่านไม่ออกจะสร้างเอกสารใหม่แทนที่จะ render ของพัง

**ผลลัพธ์ที่ผู้ใช้เห็น**
- แท็บ "ใบเสนอราคา" ข้างแกลเลอรีและผัง Flow
- แก้ราคาได้ทุกช่อง บันทึกอัตโนมัติ ทุกคนในโปรเจกต์เห็นใบเดียวกัน (ผู้ชมแก้ไม่ได้)
- กดปุ่มเดียวได้ PDF พร้อมส่งลูกค้า

**Acceptance criteria**
- แคปหน้าจอ 6 หน้า 1 modal → เปิดแท็บใบเสนอราคาต้องได้ 7 รายการ โดย modal เยื้องใต้หน้าแม่
- เปลี่ยนขนาดงาน → จำนวนวันต้องเปลี่ยนตาม default ของขนาดนั้น
- ผลรวมของคอลัมน์ "รวม" ทุกบรรทัดต้องเท่ากับยอด subtotal ที่แสดงเป๊ะ
- กดพิมพ์ → ต้องได้เอกสารที่มีเฉพาะใบเสนอราคา ไม่มี UI ของ studio ติดไปด้วย และมีภาคผนวกภาพหน้าจอครบ
- แก้โค้ดด้วย AI 1 รอบ → ข้อมูลใบเสนอราคาต้องไม่เปลี่ยน

**ปัญหา / ที่มา**
ผู้ใช้รายงานสองเรื่อง: *"มันไม่เอา sub ของหน้าจอนั้นมาด้วยอ่ะครับ"* และ *"ตอนที่ทำเอกสารผมอยากใส่รายละเอียดด้วยว่าแต่ละหน้าเป็นยังไงทำงานยังไง"*

เรื่องแรกกลายเป็น **บั๊ก 3 ตัวซ้อน**:
1. ตารางหว่านรายการจาก `shots` ครั้งเดียวตอน mount แต่คลังหน้าจออ่านจาก storage แบบ async → กดแท็บทันทีจะหว่านจากอาเรย์ว่างและบันทึกเอกสารเปล่า
2. `readOnly` ถูกต่อผิดไปที่ `!onAddScreenIndex` ซึ่ง Studio ตั้งเป็น undefined ทุกครั้งที่มีรอบแก้ไขวิ่งอยู่ → **แก้ใบเสนอราคาไม่เข้าแบบเงียบๆ ตอน AI ทำงาน**
3. แถวของ modal เก็บชื่อเป็น `"หน้าแม่ — modal"` รวมเป็นสตริงเดียว → ตารางจัดกลุ่มไม่ได้ และการเช็คว่า "มีแล้วหรือยัง" เทียบจากสตริงนั้น → **สองหน้าที่มี "ยืนยันการลบ" เหมือนกันจะยุบเหลือแถวเดียว** อีกอันหายไปและถูกนับว่าคิดราคาแล้ว

**สิ่งที่ทำ**
- รอให้อ่านคลังหน้าจอเสร็จก่อนค่อย render แท็บ · `readOnly` ใช้ค่าของโปรเจกต์จริง · แยก `parent` เป็นคอลัมน์ของตัวเอง
- **modal เยื้องใต้หน้าแม่พร้อมป้าย "↳ modal ของ …"** และหัวตารางบอก **"N หน้าจอ · M modal"** เพื่อให้ตอบด้วยตาได้ว่าครบไหม
- **`/api/screen-specs`** — AI อ่านโค้ดจริง (pages + components ทั้งหมด **กว้างกว่าตอนสแกนซึ่งอ่านแค่ navigation** เพราะการอธิบายหน้าต้องอ่านตาราง/ฟอร์ม/modal ที่อยู่บนหน้านั้น) แล้วเขียน 1–3 ประโยคภาษาลูกค้าว่าหน้านั้นทำอะไรได้ มีข้อมูลอะไร มีปุ่มสำคัญอะไร — **ห้ามพูดถึงชื่อไฟล์ ชื่อ component หรือศัพท์เทคนิค**
- **เติมเฉพาะช่องที่ยังว่าง** ไม่ทับข้อความที่คนเขียนเอง (กฎเดียวกับการซิงค์รายการ) · **ชื่อที่ไม่ได้ถามถูกทิ้ง** — หน้าที่ AI แต่งขึ้นเองจะไม่โผล่มาเป็นรายการที่คิดเงิน
- ข้อความนี้พิมพ์ใต้ชื่อรายการเต็มความกว้างในเอกสาร

**ผลลัพธ์ที่ผู้ใช้เห็น**
- ใบเสนอราคาไม่ตกหล่น modal อีก และเห็นตัวเลขยืนยันที่หัวตาราง
- แต่ละบรรทัดมีคำอธิบายว่าหน้านั้นทำงานยังไง — **ราคาเปล่าๆ คือการขอให้ลูกค้าเชื่อ ราคาที่มีขอบเขตแนบมาคือการประเมิน**

**Acceptance criteria**
- เปิดแท็บใบเสนอราคาทันทีหลังเปิดแผง → ต้องได้รายการครบ ไม่ใช่เอกสารเปล่า
- สองหน้าที่มี modal ชื่อเดียวกัน → ต้องได้ 2 แถวแยกกัน
- กด "เขียนรายละเอียดด้วย AI" → ช่องที่มีข้อความอยู่แล้วต้องไม่ถูกทับ
- คำอธิบายต้องไม่มีชื่อไฟล์หรือศัพท์เทคนิค

- **เป็นข้อเสนอ ไม่ใช่การแก้** — การ์ดแสดงช่วงตลาด/ที่แนะนำ/ของคุณตอนนี้เทียบกัน, ลิสต์**เฉพาะบรรทัดที่มันเห็นต่าง** (โชว์หมดจะกลบสองบรรทัดที่ควรเถียงกันจริงๆ) และให้ทางออก 3 ทาง: **ใช้ทั้งหมด / ใช้เฉพาะเรตต่อวัน / ไม่ใช้ กรอกเอง** · **ไม่มีทางไหนที่เขียนลงเอกสารโดยไม่กด** เพราะคนที่ต้องตอบลูกค้าเรื่องราคาคือผู้ส่ง ไม่ใช่ AI

*การวินิจฉัย (ลำดับที่ทำจริง):*
1. ตรวจจากภายนอก — เว็บเราตอบ 200 หน้า login render ปกติ JS chunk 200 `/changelog` แสดง v0.47.0 → **build ขึ้นสำเร็จ แอปเราไม่ได้พัง**

4. ผู้ใช้ส่ง log มา → **86 จาก 100 requests ยิงที่ `fittbuilder_projects` และ 79 อันเป็น 522/524** query เดียวกันซ้ำ 69 ครั้ง:
   ```
   select=id,owner_id,name,files,phase,approved_phases,history,messages,...
   ```
5. วัดขนาดจริงหลังฐานข้อมูลกลับมา — ตาราง 49 MB, **แถวใหญ่สุด E-tax_MTS = 4.9 MB** (files 260 kB + history 2.5 MB + messages 2.0 MB / 223 เทิร์น)

*สาเหตุ — แถวเดียวบรรจุ 3 ก้อนใหญ่ และเราเรียกมันซ้ำ:*
| ที่เรียก | ทำอะไร |
|---|---|
| ทุกครั้งที่เพื่อนร่วมทีมเซฟ | broadcast → อีกฝั่งดาวน์โหลดทั้งโปรเจกต์ → เซฟ → broadcast กลับ → **วนกันเอง** |
| ทุกครั้งที่สลับกลับมาที่แท็บ | ดาวน์โหลดทั้งโปรเจกต์ **เพื่อเทียบ `phase` ซึ่งเป็นข้อความสั้นตัวเดียว** |
| หน้ารายการโปรเจกต์ | ดึง `files` ของ**ทุกโปรเจกต์** มาเพียงเพื่อนับจำนวนไฟล์ |
| ทุก autosave | upsert ทั้งก้อนแล้ว**อ่านกลับมาทั้งก้อน**อีกรอบ |

พอ instance ตอบช้า → request timeout → client retry → โหลดเพิ่ม → **วงจรตาย** (ตรงกับที่เห็นใน log: 200 → 502 → 522 รัวๆ)

**สิ่งที่ทำ — แก้ 3 ชั้น**

*ชั้นที่ 1 — ต้นเหตุ (`1b5dba8`)*
- broadcast แนบ `updatedAt` ไปด้วย → ฝั่งรับ**เทียบสตริงก่อน** ไม่ใหม่กว่าก็ไม่โหลด
- `getProjectPhase()` ดึงแค่ `phase, updated_at` → โหลดเต็มเฉพาะตอน phase ต่างจริง
- `saveProject()` เขียนอย่างเดียว select กลับมาแค่ `updated_at` — เราเพิ่งส่งเมกะไบต์พวกนั้นไป การอ่านกลับมาไม่ได้บอกอะไรที่เราไม่มีอยู่แล้ว
- migration `0027` เพิ่มคอลัมน์ `file_count` ที่ trigger ดูแล → หน้ารายการโปรเจกต์ **จาก 2,799 kB เหลือ 156 bytes** (วัดจริง) · ใช้ trigger ไม่ใช่ generated column เพราะ `jsonb_object_keys()` ไม่ immutable

*ชั้นที่ 2 — ปิดรูที่โตไม่หยุด (`1f7cae4`)*
- `messages[].changes` เก็บเนื้อไฟล์ทุกเทิร์นตลอดกาล เพิ่ม ~9 kB/เทิร์นไม่มีเพดาน → **เก็บเนื้อเต็มแค่ 10 เทิร์นล่าสุด** เทิร์นเก่ายังบอกว่าแก้ไฟล์ไหนบ้าง ส่วนโค้ดจริงอยู่ใน History (content-addressed, จำกัด 30) ซึ่งเป็นที่ที่มันควรอยู่
- ตัดเฉพาะตอน**บันทึกลงฐาน** ในหน่วยความจำยังครบ — สิ่งที่ผู้ใช้กำลังดูอยู่ไม่เปลี่ยนใต้มือ
- `DiffViewer` แยกออกว่า changeset ที่ถูกตัด (null ทั้งสองฝั่ง) ต่างจากไฟล์ที่ถูกเพิ่มหรือลบ และบอกว่าไปดูโค้ดได้ที่ไหน

*ชั้นที่ 3 — กันไม่ให้เกิดซ้ำในระดับโครงสร้าง (`9bf84d1`)*
- migration `0028` ตั้ง `statement_timeout` ต่อ role (anon 10s · authenticated 15s · service_role 60s) และ `idle_in_transaction_session_timeout` · query หนักสุดที่ถูกต้องของเราใช้ไม่ถึงวินาที เพดานนี้จึงไม่มีทางไปโดนของปกติ — **แต่ถ้าอนาคตมี query พลาดอีก จะพังแค่ request นั้นแล้วขึ้น error ไม่ลากทั้งระบบลงไป**
- **`/api/health`** — รอบนี้เรารู้ว่าล่มเพราะผู้ใช้บอก ทั้งที่แอปตอบ 200 ตลอด (ตัวที่ตายคือฐานข้อมูลข้างหลัง) · endpoint นี้ตอบคำถามเดียวที่ควรตั้ง alert: **request แตะข้อมูลได้ไหม** ถ้าไม่ได้คืน 503 · ไม่ต้องล็อกอิน ไม่เปิดเผยข้อมูล อ่านแถวเดียวจากตารางเล็ก และมี timeout ของตัวเอง 5 วินาที **เพื่อไม่ให้ตัว probe กลายเป็นภาระที่มันมีหน้าที่ตรวจจับเสียเอง**
- `/api/health` และ `/api/version` เป็น public ใน proxy — monitor ที่อ่าน redirect ไป `/login` จะรายงานว่า "up" ทั้งที่ระบบล่ม

**ผลลัพธ์ที่ผู้ใช้เห็น**
- ทำงานร่วมกันหลายคนไม่ทำให้ระบบช้าอีก
- หน้ารายการโปรเจกต์เปิดเร็วขึ้นชัดเจน
- ถ้าเกิดปัญหาอีก จะพังเฉพาะจุดและมีตัวแจ้งเตือนแทนที่จะล่มทั้งระบบเงียบๆ

**Acceptance criteria**
- สองคนแก้โปรเจกต์เดียวกันพร้อมกัน → ต้องไม่มีการดาวน์โหลดโปรเจกต์เต็มเมื่อ `updatedAt` ไม่ใหม่กว่า

- โปรเจกต์ที่มีมากกว่า 10 เทิร์น → ขนาด `messages` ต้องไม่โตขึ้นตามจำนวนเทิร์นอีก
